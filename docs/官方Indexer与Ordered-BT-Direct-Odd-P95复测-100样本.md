# Ordered Indexer＋BT Direct Odd Plan：100K P95 尾部复测

## 结论

- 对 `batch=9/10/11、context=102400` 分别做了两轮独立的 100 样本复测，正式候选样本合计 600 次；全部正确性检查通过。
- 偶发 kernel 间隙确实会重现。两轮中 Gap 大于 1μs 的次数为 **52/600（8.67%）**，并且 batch 之间的发生率会随运行而变化。
- 三个工况的 P50 都非常稳定，Indexer 约 174～175μs、Plan 约 50～52μs、Gap P50 均为 0.022μs。
- P95 不稳定来自“尾部 Gap 在本次运行中是否超过 5%”这一概率边界，当前不能把某一轮的 P95 当作固定算法开销。
- 当前数据进一步把问题定位到两次独立算子调用之间：设备 kernel Duration 稳定，设备时间线中偶尔出现 10～524μs 的 kernel 间空闲。

## 解释

当前链路从第一次 Indexer 调用返回 Python 后，再发起第二次 Plan 调用。正常时 Plan 会在约 174μs 的 Indexer 执行结束前进入同一 stream，因此 Gap 为 0.022μs。主机侧偶尔调度该第二次调用较晚时，设备在 Indexer 完成后等待，形成几十到几百微秒的空洞。

100K 比 350K 敏感，因为 350K 的 Indexer 执行约 600μs，给主机预留了更长下发窗口。该现象与 batch9/10/11 的算法规模没有单调关系，并在两轮测试中互换高 P95 的 batch，符合主机下发或调度抖动。
