# Official Indexer 与新 Bitmap Plan 同场对照

固定 MTP3、TopK2048、capacity8192、`full_cache_90pct`。每个 query row 初始恰好 1843 个 resident hit、205 个 miss。
单位 μs；`chain` 是同 stream 上 ordered Indexer → 独立 Plan 的 span，包含两 kernel 间偶发空闲。
Official 只包含原始 Indexer；其余两路都包含保序 Indexer、独立 Plan 和两 kernel 间隙。
所有数据是设备 profiling 的 kernel Duration/时间戳；未测 Transfer、SFA 或端到端框架开销。

## 执行结论

- 18/18 工况通过；每路每工况 20 个正式样本，共 1080 个正式测量。
- 两个 Plan 在全部 18 个工况均为联合执行，联合组数等于 Batch，回退组数为 0。
- 每行初始严格为 1843 hit、205 miss；Official 与 Ordered TopK 的逐行 token 集合完全一致。
- Bitmap Plan 相对旧 BT Plan 的分 context 几何平均：100K Plan P50 `0.980×`（快 2.0%），358K Plan P50 `0.872×`（快 12.8%）。
- 包含保序 Indexer 和独立 Plan 的整链相对 Official：100K P50 `1.297×`，358K P50 `1.098×`。这里包含保序改造、Plan 和两 kernel 间隙，不能全部归因于 Plan。

## 执行耗时

正式矩阵从 18:16:23 到 18:25:56，墙钟约 9 分 33 秒。`batch8` 约 123 秒，其中包含首次 QLI torch extension 构建；后续各 batch 约 49–63 秒。18 个 context 内部记录的 fixture、warmup、正式采集、校验和导出阶段合计约 313 秒；剩余时间主要是每个 batch 独立启动 Python/NPU 上下文、加载算子库、编译缓存检查、读取回传和收尾。

慢的主因是实验矩阵和 profiling 流程，不是 kernel 本身：

- 9 个 Batch × 2 个 context × 3 路实现。
- 每路每工况 10 次预热、20 个正式样本和 2 次回归检查，并逐步做完整 TopK/输入/状态/输出/保护区校验。
- 每个 context 单独启动 CANN profiler、同步解析 trace 并导出 CSV；idiomatic kernel 只有约 50–600 μs，但 profiler 的准备、落盘与解析是秒级。
- 正式运行前曾出现两次无效 smoke：一次 QLI torch extension 身份不对，一次 mask264 的外部 BT 实现没有进入设备库。两者都在数据采集前失败，已修复；不计入本轮样本。

## 解释边界

- 保序 Indexer 相对 Official 的 P50 差值范围为 -157.183～+7.219 μs；因此整链开销不能全部归因于 Plan。
- 新 Bitmap 与旧 BT 在本轮同库、同输入、同设备运行；它们之间的 Plan 差值才是本轮最直接的新旧算法对照。
- `joint/fallback` 对所有 18 个工况均为 batch/0，说明测试输入实际进入联合路径。
- 目标 kernel `sparse_kv_plan_joint_kernel_ordered_bitmap_512` 已出现在本轮 profiling inventory。
- Plan 库 SHA256：`71df45dff86de479fc48e38d987a14ddc010c330ce7bd94d4d6baa7028e9e388`。
