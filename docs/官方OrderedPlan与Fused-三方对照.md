# Official、Ordered＋BT Direct Odd Plan 与 OrderedFused 三方对照

## 测试目标

- **Official**：官方 `quant_lightning_indexer`，不执行 Plan。
- **Ordered＋Plan**：`quant_lightning_indexer_ordered` → `joint_mtp3_bt_direct_odd_512`，两个独立算子顺序下发。
- **Fused**：GitCode `wzj_qli_order_fused` 当前分支中的 `quant_lightning_indexer_ordered_fused`，一次融合算子调用，内部使用该分支自带的 Plan。

三方输入完全相同。固定 MTP3、TopK 2048、capacity 8192、batch 8～16、context 102400/358400、90% 满缓存；每行命中 1843/2048，miss 205。每工况预热 10 次、正式 20 样本、回归检查 2 次。

## 核心结果

- 18/18 工况全部通过正确性检查；官方、Ordered 和 Fused 的 TopK token 集合逐行一致。
- Ordered＋Plan 与 Fused 均为每请求联合执行，全部 `0` 回退。
- Fused 在全部 18 个工况都慢于 Ordered＋BT Direct Odd Plan。
- 100K：Ordered/Official P50 几何平均 **1.303×**，Fused/Official **1.971×**，Ordered/Fused **0.661×**。也就是当前 Ordered＋Plan 的 P50 约为 Fused 的 66.1%，比 Fused 快约 33.9%。
- 350K：Ordered/Official **1.091×**，Fused/Official **1.478×**，Ordered/Fused **0.738×**。当前 Ordered＋Plan 比 Fused 快约 26.2%。
- Fused 在 100K 下为约 343～347μs；350K 下为约 884～887μs。其额外耗时随 context 增长明显。
- Ordered＋Plan 的 P50 在 100K 为约 224～231μs，350K 为约 648～659μs。
- 100K 下 Ordered 路径存在此前的偶发两-kernel 间隙，因此其 P95 波动较大；Fused 的 P95 更稳定，但绝对中位数明显更高。

这里比较的是两个完整系统。Fused 内部 Plan 与 `joint_mtp3_bt_direct_odd_512` 并非同一实现，因此结果不能拆成单纯的“融合调用开销”。
