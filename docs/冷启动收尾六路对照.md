# 冷启动专用收尾：六路一次完成

基于 `551f58b`，新增两条候选，不替换已上机验证的参考实现。本分支只做CPU源码/语义检查，尚未完成本机CANN9.1编译或NPU验证，不预填任何性能数据。

## 固定六路

| 实现 | MTP0 | MTP1/3 |
|---|---|---|
| abcdf_pages | 原带页表ABCDF | 原带页表ABCDF |
| joint_hw_ac_512 | 原1024线程逐行路径 | 原AC，512线程联合阶段 |
| joint_hw_ac_256 | 原1024线程逐行路径 | 原AC，256线程联合阶段 |
| joint_union_base_512 | 原512线程单行有序路径 | 原base512联合路径 |
| joint_union_cold_512 | base512 + reset专用收尾 | base512 + reset专用收尾 |
| joint_hw_ac_cold_512 | 保留原1024线程逐行路径 | AC512 + reset专用收尾 |

所有private回退仍为1024线程。AC256只改联合阶段线程配置，不引入单行有序协议。两条冷候选不启用上一轮的新ABCD，不改变miss尾部清理约定。

## 触发条件与算法

严格复用父版条件：当前请求ID与缓存最后ID不一致，或当前缓存mode与需要的private/joint协议不一致。缓存为空、命中为零、stable prefix导致全部失效，都不能代替这个reset条件。

归并、去重、因果有效性、容量检查与回退沿用父版。成功构建有序并集并且明确reset时：

```
u = 唯一有效token数，先确认u <= capacity
slot_to_token[s] = unique[s] if s < u else -1
miss_tokens[uid] = unique[uid]
miss_slots[uid] = uid
current_slots[query] = query_to_uid[query]，无效query为-1
lru = [u, ..., capacity-1, 0, ..., u-1]
miss描述符未使用尾部写-1
发布原private或joint/follower的mode及resident映射
只更新leader的last_req_id
```

这省去了reset状态下的owner初始化、resident分类、LRU partition Scan和miss分配Scan。联合前面的归并/去重仍然执行，不能据此宣称冷路径必然超过ABCDF。

**同请求的warm全miss仍走父版热路径**，以保留既有LRU；否则identity分配会改变淘汰语义。

## 保持不变的部分

- `sorted_sweep_stage.h`、`sorted_sweep_controller.h`、`union_next_stage.h`及ABCDF计算文件保持不变。
- `cold_ac_stage.h`、`cold_union_stage.h`分别是父版副本，仅在reset判断后增加一个分支；构建身份检查会逐字验证这一约束。
- 公共ID123使用base512算法配置90，公共ID124使用AC512算法配置72；生成包装额外定义 `JOINT_COLD_FINISH`。没有把旧配置整体重命名为新算法。
- 共享收尾位于 `cold_finish.h`；原VF签名、GM/UB地址空间、线程数、工作区布局与tiling大小不变，不增加设备输出或打点。
- 超容量、不支持的值域/行数、单行重复token等继续走原回退。
- 热路径保留原算法，但编译后资源分配仍可能改变，因此热性能必须同场复测。

## 同步与状态

reset分支内先执行block barrier：确保所有线程已捕获相同reset判定，再允许thread1发布mode、thread0写last_req_id。结束前再次执行block barrier，之后才能复用本AIV scratch。热分支不新增该barrier。

| producer → consumer | 数据 | 约束 |
|---|---|---|
| 原归并/去重 → 冷收尾 | UB/GM unique、query map、ctx | 保留父版controller的V→S等待与VF边界 |
| reset读取 → mode/ID写入 | 原GM row_modes/last_req_ids | reset分支开始的block barrier |
| 冷收尾 → 下一组scratch复用 | cache/LRU/输出/ctx | 收尾末尾的block barrier |

继续由thread1写mode。这是历史错写问题的经验规避，不宣称底层根因已经确认。CPU计数器只用于检查真实冷函数是否进入，设备构建没有该计数器。

## CPU与服务器门禁

CPU执行真实候选helper及父版，在UB/GM模型中逐字段比较所有输出与持久状态，包括完整miss尾部、follower未改字段、输入不变性及保护区。覆盖空并集、满容量、溢出回退、重复token/resident、非法/未来token、非活动行、请求ID变化、冷→热续用及同请求全miss。另用观察计数器确认触发条件；这些检查不是NPU仿真或性能验证。

NPU门禁沿用现有完整保护与golden检查，并增加每种MTP的8步连续调用：

1. 冷调用。
2. 续用同一请求的设备状态。
3. 同请求下改成全部miss，保留旧LRU语义。
4. 更换请求ID。
5. 续用新请求状态。
6. 拆成单行片段，或MTP0加入重复token。
7. 恢复请求分组。
8. 再续用设备状态。

这些连续步骤不恢复持久状态、不用golden覆盖设备输出。其他审计与性能采样仍在每次调用前恢复各自相同初始状态；恢复不计入目标kernel。输入错写回归默认5次，无100/1000次额外展开。

## 报告与失败现场

根目录 `report.md`展示P50/P95、样本数、相对ABCDF/AC512以及冷候选相对自身父版的耗时比。所有比值为候选/参考，小于1表示更快。

`confirm/joint_matrix_*/capture_metadata.json`保留实际输入指纹、设备/编译/库身份、逐工况miss/descriptor数、每个样本及相对自身MTP0的比值；`data_index.json`索引原始CSV。`gate.json`保留全部正确性及连续调用结果，`RUN_STATUS.json`记录阶段。失败立即停止、保留原始异常与现场，不生成成功报告。数据留在运行机器，不上传输入、采集数据或二进制。

这里仍然只测Plan；即使描述符减少，也不能直接称为Plan→Transfer/SFA端到端加速。冷启动捷径的收益及热路径资源变化，都等待服务器实测。
